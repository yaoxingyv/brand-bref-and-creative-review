# 品牌创意简报与评审系统 · 试点版

> 面向「客户访谈 → 需求确认 → 创意提案 → 品牌审核 → 交付」这条链路的简报管理与评审系统。
> 需求来自《与各个负责人对话形成的报告》（36 条事实），功能边界来自《品牌创意简报系统-项目方案与报价单》的 M1–M9 模块与七条硬约束。

**这不是一个问答机器人。** 它的核心是把简报做成一等公民对象：结构化、版本化、可追溯、可验收。

---

## 一、它解决什么

访谈里四个可归因的失败模式，本系统逐一对应：

| 现状问题 | 事实 | 系统怎么解 |
|---|---|---|
| 客户口头补的约束没进简报，设计反复返工 | f10 / f15 | 一页式缺项清单，每条附来源位置 |
| 版本靠文件名猜，交接各说各话 | f24 / f23 | 双条件（有效期 + 确认状态）判定 + 交接登记卡 |
| 三类工具没统一编号，只能人工比对 | f30 / f31 | 统一关联编号 + 字段级脱敏只读导出 |
| 事后补表导致旧结论覆盖新结论 | f13 / f34 | 双时间戳（业务发生 / 系统接收），过期来源拦截 |
| 不知道谁批的、用哪版批的 | f45 | 全量审计留痕，含"谁试图越界" |

## 二、七条硬约束（红线）

来自 f05 / f14 / f22 / f32 / f41 / f44 / f52，**写在代码常量里，不提供配置开关**——
红线如果可以被配置关掉，就等于没有。

| 编号 | 约束 | 依据 |
|---|---|---|
| R1 | 模型没有审批权限 | f22 |
| R2 | 正式结论须由授权人员确认 | f41 |
| R3 | 建议不能覆盖原值或省略确认 | f14 |
| R4 | 只开放脱敏只读导出 | f32 |
| R5 | 不自动发布广告 | f05 |
| R6 | 不推断或承诺法律审查结果 | f05 / f52 |
| R7 | 无法确认版本或关键字段时不得默认通过 | f44 |

定义位置：`app/core/config.py` 的 `HardRules`。违反时抛 `HardRuleViolation`，
返回 403/409 **并写一条带 rule_code 的审计日志**。

## 五、关键设计决定

**1. 规则引擎打底，大模型只做软活**
版本是否有效、来源是否过期、字段是否缺失——全部由 `agents/rules.py` 的纯函数判定。
原因：审核要的是可解释结论（f45），大模型的黑箱结论傅景不会签字；
而且红线不能交给概率。当前版本**零外部依赖即可跑通**，未接大模型也能完整演示。

**2. 缺失值与未确认值分开**（f31）
`None` = 没填（要补录），`status=unconfirmed` = 填了没确认（要催确认）。
混为一谈会让秦芮的数据质量检查失效。

**3. 授权名单查库，不查角色**
角色是代码常量，授权名单是**客户尚未书面确认**的业务决定（访谈明确标注"待核实"）。
写死在代码里等于替客户做决定，验收必被打回。

**4. 拦截要留痕，不只是拒绝**
每次越界都写 `audit_logs` 并带 rule_code——"谁试图越界"本身就是审计要的证据。

**5. 示例简报刻意残缺**
不填单一诉求（行业调研指出的头号痛点），30 项约束只确认 11 项。
打开系统就能看到缺项清单长什么样——如果种子数据是完美的，等于没演示。

## 六、当前状态与边界

**已完成（M1–M4、M6、M7、M9）**：授权确认、审计留痕、简报结构化、缺项清单、版本双条件判定、过期来源拦截、人工队列、素材授权标记。

**未实现**：
- M5 只读集成（三类工具的真实连接器）—— 需要客户确认主记录来源与导出粒度
- M8 效果观测台账 —— 基线是虚构样本（f12），不设量化承诺
- 资产版本栈与批注锚点（图片坐标 / 视频帧 / PDF 锚点）—— 这是行业调研指出的核心壁垒，工作量大
- 大模型接入（规则引擎已够跑通，接模型只需配 `.env` 的 `LLM_PROVIDER`）

**试点边界（f03 / f05）**：四周试点、两名业务骨干、每周投入不超四小时；
只覆盖一个批次；不自动发布广告；不推断法律审查结果。

**待客户确认的事项**（访谈报告列了 8 项，都会影响实现）：
主记录来源是哪类工具、脱敏导出粒度、授权确认人名单、异常拦截标准、
"已确认新版本"以哪个工具为准、缺项清单字段构成、保留期限、试点是单品牌还是多品牌。
